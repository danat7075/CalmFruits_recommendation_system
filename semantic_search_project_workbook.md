## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача — построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

**Данные.**

В проекте четыре файла. Три из них — рабочие, к ним вы будете обращаться постоянно, один — служебный, нужен для одного этапа проекта.

**Итоговые артефакты проекта:**

- Jupyter-тетрадь с EDA, пайплайном и оценкой качества системы;
- эксперименты, логируемые в MLflow;
- этот документ, заполненный по ходу работы;
- дополнительная часть проекта — Streamlit-приложение.

## 1. Наблюдения по данным (EDA)

### Вопросы

Ответы записывайте прямо здесь, рядом с полем «Ответ».

- **Размер и структура.** Сколько в каталоге строк? Сколько уникальных `imt_id` и `nm_id`? Есть ли дубликаты по `imt_id`?
- **Почему это важно.** `imt_id` — карточка товара, `nm_id` — конкретный артикул, то есть некоторый вариант товара с отличным цветом, размером или другой характеристикой. Если индексировать артикулы, один товар будет несколько раз конкурировать сам с собой в выдаче.
- **Ответ:**  В 200 000 строках содержится 174 427 уникальных карточек и 199 957 уникальных артикулов. Полных дубликатов нет, но есть 25 573 повторных вхождения `imt_id` и 43 повторных вхождения `nm_id`. Повтор карточки обычно связан с её вариантами: максимум — 30 разных артикулов на карточку, а у 90% карточек только один артикул.

Поэтому индекс строится на уровне `imt_id`: иначе варианты одной модели могли бы занимать несколько мест в выдаче. Причина 43 повторов `nm_id` отдельно не установлена.


- **Полнота полей.** Какова доля пропусков в колонках в `description`, `nm_colors_names`, `brand_name`, `subj_name` с учётом пустых строк?
- **Почему это важно.** У товаров без описания текст для эмбеддинга состоит только из названия и категории, это может влиять на качество их поиска. Пропуски часто закодированы пустой строкой, а не NaN.
- **Ответ:**  Проверка только `NaN` дала бы нулевые значения, однако пустые строки встречаются часто: описание отсутствует у 28,75% строк, цвет — у 17,11%, название — у 0,35%, бренд — примерно у 0,10%. В предметной категории обнаружено восемь пустых строк — 0,004% исходных данных. Эти доли относятся к исходным строкам, до объединения вариантов карточек.

Удаление всех товаров без описания привело бы к значительной потере каталога. Поэтому карточки с названием сохраняются даже при отсутствии описания. Удаляются только карточки, у которых одновременно пусты название и описание.

По рекомендации Q&A (02:22–09:05) добавлен просмотр частых значений и возможных текстовых заглушек во всех семи текстовых полях. Возможные текстовые заглушки проверяются отдельно. Автоматическая замена не применяется, поскольку не каждое такое значение является пропуском.


- **Категории.** Какие корневые категории `subj_root_name` есть в данных и в каком соотношении? Сколько уникальных `subj_name`, какие из них самые частые, а какие — самые редкие?
- **Почему это важно.** Распределение по категориям определяет, на каких товарах система будет проверяться чаще всего. Редкие категории, в которые входят 1–2 товара, — кандидаты на особые случаи в разметке и оценке.
- **Ответ:**  В выгрузке 64 заполненные корневые категории и 3 233 заполненные предметные категории. Пустая строка даёт ещё одно значение в каждом из этих полей. У восьми карточек корневая категория не указана. Наиболее крупная категория — одежда: 36 965 карточек. В обуви 11 524 карточки. Для 820 предметных категорий представлено всего по одной-две карточки, поэтому единая оценка по всему каталогу скрывала бы сильную неоднородность данных.


- **Длина текстовых полей.** Какое распределение длины признаков `imt_name` и `description` в словах и символах? Есть ли в данных выбросы — экстремально длинные описания?
- **Почему это важно.** Длина текста связана с выбором модели эмбеддингов, так как влияет на лимит токенов и на решение о шаблоне конкатенации полей. Слишком длинные SEO могут размывать эмбеддинг.

Поэтому название удобно поставить в начало `product_text`, а описание использовать как источник назначения и характеристик.

Количество слов не равно количеству токенов модели. Решение о допустимой обрезке принимается ниже по токенизатору E5, отдельно для подготовленного каталога оценки. 


- **Качество текста.** Просмотрите вручную 20–30 случайных карточек. Есть ли в данных HTML-теги, спецсимволы, артикулы внутри названий, шаблонные повторяющиеся описания, описания, не относящиеся к товару?
- **Почему это важно.** В результате осмотра карточек вы сможете сформировать прямой вход для функции очистки текста. Всё, что не заметите здесь, попадёт в индекс.

Поэтому очистка убирает HTML, управляющие символы и лишние пробелы, но сохраняет числа, дефисы и обозначения моделей. Массовое удаление «рекламных» слов без отдельной проверки не применяется, чтобы не потерять полезные признаки.

У разных товаров встречаются одинаковые описания. Пока они сохранены: без дополнительной проверки их удаление может привести к потере полезных характеристик.

Упоминания бренда и цвета в названии или описании сохраняются. После дедупликации в атрибутах остаётся цвет выбранного варианта карточки.

- **Ответ:** В train 11 453 пары, 700 запросов и 2 285 товаров. В среднем 16,36 оценённых товаров на запрос, медиана 16, минимум 1, максимум 31.

## 2. План базового пайплайна

**2.1. Формулировка задачи своими словами**

Система ищет карточки товаров по текстовому запросу. Каталог подготовлен из raw-выгрузки; объект выдачи — imt_id. TF-IDF сравнивается с multilingual-e5-base на общей validation-выборке по метрикам ранжирования. Цель первой итерации — определить, даёт ли семантический поиск основания для дальнейших экспериментов.

**2.2. Подготовка данных**

**Выбор раздела.** Положительные пары в `train_fit` относятся к двум корневым категориям: 379 запросов связаны с одеждой и 146 — с обувью. Поэтому фактически выбраны **«Одежда» и «Обувь»**, хотя код допускает до трёх категорий. Это соответствует ответу наставника на Q&A (09:15–09:45): MVP ограничивается категориями с проверенной разметкой. Данные test для выбора не использовались.

**Дедупликация и текст карточки.** При выборе строки для одного `imt_id` сначала сохраняется вариант с непустым названием, затем с наиболее длинным описанием, а при равенстве — с меньшим `nm_id`. Это простое воспроизводимое правило: название задаёт тип товара, длина описания приближённо отражает объём доступных характеристик. Длина не гарантирует полезность текста, поэтому длинные описания дополнительно просмотрены в EDA. Конфликтов корневой категории внутри карточки не найдено.

Удалены 113 карточек без названия и описания. После подготовки в двух категориях осталось 48 376 карточек. Карточки с названием, но без описания, сохранены.

Для поиска используется текст из названия, предметной категории и описания. Описание сохраняет сведения о назначении и свойствах товара, которых может не быть в названии. Это соответствует ответу наставника (10:46–12:03). Поля разделены точкой; пустые поля не превращаются в строки `nan` или `None`.

**Качество текста, бренд и цвет.** Для просмотра выбраны 25 строк с фиксированным seed. В них встречаются полезные числовые характеристики и обозначения моделей, например размер сумки 13,3 дюйма и совместимость чехлов с моделями телефонов, а также рекламные формулировки. Поэтому очистка убирает HTML, управляющие символы и лишние пробелы, но сохраняет числа, дефисы и обозначения моделей. Массовое удаление «рекламных» слов без отдельной проверки не применяется, чтобы не потерять полезные признаки.

У разных товаров встречаются одинаковые описания. Пока они сохранены: без дополнительной проверки их удаление может привести к потере полезных характеристик.

HTML найден примерно в 0,01% описаний. Непустых брендов — 13 318. Хотя бы один цвет из отдельного поля буквально встречается в названии у 2,65% строк с заполненным цветом. Проверка не учитывает склонения, поэтому это оценка точных совпадений, а не полного смыслового дублирования.

Отдельные поля `brand_name` и `nm_colors_names` не добавляются в `product_text`. Исключение отдельного поля бренда соответствует ответу наставника на Q&A (12:04–15:02). Упоминания бренда и цвета в названии или описании сохраняются. После дедупликации в атрибутах остаётся цвет выбранного варианта карточки.

**Каталог для оценки.** Из 48 376 подготовленных карточек выделен общий пул оценки — 4 256 ID из `wb_products_dedup.parquet`. Все ID пула найдены в raw-каталоге. Тексты и признаки сформированы из raw, а служебный файл задаёт только множество кандидатов. Ограничение выдачи и расчёта метрик этим пулом прямо подтверждено наставником на Q&A (10:00–10:45).

После ограничения домена сохранены все 175 validation-запросов; положительных пар вне каталога оценки нет, запросов без доступного релевантного товара тоже нет. Таким образом, в этом запуске фильтрация не уменьшила число положительных validation-пар. Поиск каждого метода идёт по всем 4 256 карточкам, а не только по оценённым товарам конкретного запроса. Оба метода проверяются на одинаковых запросах, разметке и каталоге товаров.

**2.3. Лексический поиск (baseline)**

**Лексический baseline.** TF-IDF выбран как простая воспроизводимая точка отсчёта. Униграммы и биграммы `(1, 2)` позволяют учитывать отдельные слова и сочетания вроде «зимние сапоги». Ограничение словаря в 100 000 признаков сдерживает размер матрицы; фактическая матрица имеет форму `(4256, 100000)`, то есть лимит достигнут. Это стартовое ограничение ресурсов, а не найденный оптимум.

`min_df=1` сохраняет редкие слова, которые могут быть значимыми названиями и артикулами. `sublinear_tf=True` уменьшает влияние повторения одного слова в описании. Значения `float32` сокращают память матрицы. Запрос проходит ту же очистку, а векторизатор приводит регистр и нормализует векторы, поэтому скалярное произведение соответствует косинусному сходству. При равных оценках сохраняется порядок по `imt_id`, чтобы выдача была воспроизводимой.

**2.4. Семантический поиск**

**Семантическая модель.** Модель multilingual-e5-base преобразует запросы и товары в векторы. К запросам добавляется префикс query:, к товарам — passage:. Поиск сравнивает запрос со всеми 4 256 товарами по косинусной близости и возвращает наиболее похожие.
Векторы рассчитываются на GPU партиями по 32 товара и сохраняются вместе с ID. Это начальный размер партии, отдельный подбор скорости не проводился. При повторном запуске ячейки векторы рассчитываются заново.
Тексты ограничены 512 токенами; обрезка затрагивает 1,25% карточек. Название и категория стоят в начале, чтобы сохранить их при обрезке описания.

**2.5. Оценка качества**

Из 700 запросов 525 оставлены для дальнейшего обучения и 175 — для проверки качества. Разбиение учитывает нормализованный текст запроса, чтобы одинаковые запросы не попали в обе части. Доля проверки 25% выбрана как начальное рабочее решение.
Оба метода проверяются на одном каталоге из 4 256 товаров. Рассчитываются Precision, Recall, HitRate и NDCG при K=5 и K=10, а также MRR по полной выдаче. Для бинарных метрик релевантными считаются оценки 2 и 3; NDCG учитывает исходную шкалу 0–3. Неразмеченные товары получают 0, результаты усредняются по запросам.
В проведённой проверке на 100 запросах ограничение каталога повысило метрики без изменения модели. Поэтому результаты разных каталогов нельзя напрямую сравнивать.
Оценки test не используются: из него читаются только ID и тексты запросов для проверки пересечений с train.

**2.6. Результаты базового сравнения**

**Выводы по первой итерации.** Методы сравнены на 175 validation-запросах и общем каталоге из 4 256 товаров. Условия расчёта метрик приведены в разделе 2.5.

| Метрика | TF-IDF | multilingual-e5-base |
|---|---:|---:|
| Precision@5 | 0,0663 | 0,1966 |
| Recall@5 | 0,1667 | 0,4775 |
| HitRate@5 | 0,2343 | 0,6171 |
| NDCG@5 | 0,3521 | 0,4725 |
| Precision@10 | 0,0669 | 0,1280 |
| Recall@10 | 0,3266 | 0,5850 |
| HitRate@10 | 0,4343 | 0,6914 |
| NDCG@10 | 0,4317 | 0,4891 |
| MRR | 0,1690 | 0,5113 |

E5 превосходит TF-IDF по всем рассчитанным метрикам. Recall@10 вырос с 0,327 до 0,585, NDCG@10 — с 0,432 до 0,489. Хотя бы один размеченный релевантный товар найден в первых десяти результатах для 69,1% запросов против 43,4%.
Ручной просмотр показал, что оба метода могут ошибаться в характеристиках товара. По запросу «шелковые топы» на втором месте E5 показал товар «Топ на тонких бретельках/шелковый (вискоза 100%)».
Результаты дают основания продолжать эксперименты с семантическим поиском. Для вывода о готовности к внедрению данных недостаточно: запросы синтетические, разметка неполная, рассмотрены только две категории. На следующем этапе можно проверить сокращение длинных описаний, отдельный учёт бренда и сочетание двух методов поиска. Эти варианты пока не оценивались.



**2.7. Риски и открытые вопросы по итогам недели**

Открыты вопросы об окончательных метриках и пороге релевантности, обязательности дообучения, доступных ресурсах и составе финальной проверки. Пока используются обоснованные рабочие настройки.
Основные ограничения результатов: синтетические запросы, неполная разметка и две категории товаров. Ручная проверка выявила ошибки по материалу, а 1,25% текстов обрезаются. Статистическая значимость различий не проверялась.
