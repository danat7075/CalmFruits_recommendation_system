# CalmFruits: семантический поиск товаров

MVP ищет карточки товаров по текстовому запросу. Сравниваются лексический TF-IDF и открытая модель `intfloat/multilingual-e5-base`. Объект выдачи — карточка `imt_id`; варианты `nm_id` объединяются при подготовке каталога.

## Текущее состояние

Выполнены EDA, два baseline, три эксперимента и финальная оценка на test. Используются порог релевантности 2 и K=1/3/5/10. Для MVP выбрана E5: на validation её NDCG@10 составил 0,4891 против 0,5085 у гибрида RRF, но она лучше по NDCG@5, Recall@10, Precision@1 и MRR.

На 300 test-запросах E5 получила NDCG@10 = 0,5001, RRF — 0,4975, словесный TF-IDF — 0,4107. Преимущество RRF по NDCG@10 на validation не повторилось. E5 лучше по качеству начала выдачи и Recall@10. Параметры по test не настраивались. MRR@10 в итоговой таблице получена из сохранённых метрик каждого test-запроса без повторного поиска.

Все пять текущих validation-runs и пять финальных test-runs завершены в MLflow; параметры, метрики и артефакты проверены. Предыдущий сохранённый запуск завершился без ошибок, флаг test возвращён в False. После исправлений ревью обновлённые ячейки нужно выполнить с этим флагом; повторный расчёт test не требуется. Streamlit пропущен как необязательное задание.

## Файлы

- `semantic_search_project.ipynb` — единая тетрадь: EDA, подготовка, baseline, эксперименты, MLflow, финальная оценка и анализ ошибок.
- `semantic_search_project_workbook.md` — Q&A, решения, наблюдения и выводы.
- `requirements.txt` — зафиксированные версии библиотек из рабочего окружения.
- `.env.example` — пример конфигурации без действующих ключей и пароля.
- `check_mlflow.py` — проверка эксперимента MLflow из задания.
- `baseline_metrics.csv`, `validation_metrics.csv`, `final_test_metrics.csv` — таблицы результатов. Все три таблицы созданы; первая и вторая относятся к validation, третья — к финальному test.
- `error_analysis.csv` — заполненный ручной разбор трёх слабых запросов E5; тетрадь читает его и загружает в MLflow.

Исходные данные скачиваются из бакета `s3-ds-source` через `https://storage.yandexcloud.net` в `files/`. `wb_products_raw_sample.parquet` даёт тексты и признаки, `wb_products_dedup.parquet` — список карточек оценки, `queries_synthetic_train.parquet` — разметку для обучения и validation. Из test до финального этапа читаются только query_id и query_text для проверки пересечений и item_id для проверки покрытия каталога; оценки relevance не читаются.

## Подготовка окружения

Команды выполнять из папки с тетрадью. Рабочая среда автора — Linux, Python 3.14.4, PyTorch с CUDA cu132. Файл зависимостей закрепляет всё окружение; совместимость этих версий с другой версией Python или бесплатным GPU Colab/Kaggle отдельно не проверена.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m ipykernel install --user --name calmfruits --display-name "CalmFruits"
cp .env.example .env
```

Заполнить в `.env` выданные ключи S3 и переменные `MLFLOW_TRACKING_URI`, `MLFLOW_TRACKING_USERNAME`, `MLFLOW_TRACKING_PASSWORD`. Выбрать ядро CalmFruits в редакторе тетради. Установка библиотек не перезаписывает requirements; после первой установки нужно перезапустить ядро.

Для загрузки артефактов задан `MLFLOW_S3_ENDPOINT_URL=https://storage.yandexcloud.net` и регион `AWS_DEFAULT_REGION=ru-central1`. MLflow использует те же ключи `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`, что и загрузка данных. Переменная `S3_ENDPOINT_URL` сама по себе не настраивает хранилище MLflow.

Модель при первом запуске скачивается с Hugging Face. В тетради закреплён revision `d128750597153bb5987e10b1c3493a34e5a4502a`, использованный в сохранённых экспериментах. CUDA используется при доступности, иначе выбран CPU. Веса и кодировщик одинаковы для товаров и запросов; E5 получает префиксы `passage:` и `query:` и нормализованные векторы.

## Порядок запуска

1. Подготовить окружение и локальный `.env` по инструкции выше. Выбрать ядро CalmFruits.
2. Оставить `RUN_FINAL_TEST_EVAL = False`, выполнить Restart Kernel → Run All. Это воспроизведёт EDA, baseline и три эксперимента на validation и создаст новые MLflow-runs. Ветка else загружает `final_test_metrics.csv` из корня репозитория и показывает сохранённые финальные показатели. Ячейка разбора ошибок читает корневой `error_analysis.csv` и логирует заполненный файл.
3. Проверить таблицы, графики и выводы, затем выполнить проверку MLflow, указанную ниже.

Авторская финальная оценка test уже завершена; повторять её для подбора конфигурации нельзя. Для независимого воспроизведения в чистой копии сначала выполнить validation с флагом False, затем один раз включить True в блоке `# Финальная оценка выполнена; оставляем False для последующих запусков.` и выполнить этот блок и следующий `if RUN_FINAL_TEST_EVAL:`. После завершения вернуть флаг в False и сохранить outputs. Существующий `artifacts/final_test_metrics.csv` блокирует повторный финальный прогон. Выбор и параметры по test не меняются.

В репозиторий для сдачи входят тетрадь, workbook, README, requirements, `.env.example`, `.gitignore`, `check_mlflow.py`, три CSV-таблицы метрик и `error_analysis.csv`. Локальный `.env`, исходные Parquet-файлы, `artifacts/` и кеши не включаются в Git. Streamlit и артефакты приложения не требуются.

Используются SEED=42, разбиение train на 525 обучающих и 175 validation-запросов, test из 300 запросов и единый каталог из 4 256 товаров. Категории — одежда и обувь; покрытие разметки проверено. Golden-сет сохраняется в `artifacts/golden_set/` с хешами файлов и загружается в каждый run. Данные для test сохраняются отдельно, их оценки не используются при выборе метода.

## Метрики и эксперименты

Релевантность ≥2 используется для Precision, Recall, HitRate и MRR. NDCG учитывает оценки 0–3 с gain=2^relevance−1. Метрики @K считаются при K=1/3/5/10, MRR — по полной выдаче, дополнительный MRR@10 — по первым десяти результатам; результаты усредняются по запросам. Неразмеченный товар получает 0. Это правило оценки, а не подтверждение его фактической нерелевантности.

Итоговый метод выбран по совокупности NDCG@10, качества первых позиций и полноты поиска. Изменяется один компонент за эксперимент. Первые предложения сравниваются с E5 baseline; символьные признаки — с TF-IDF; RRF — с обоими baseline. Отрицательный результат фиксируется как вывод, а не скрывается. Дообучение рекомендовано наставником, но необязательно при наличии минимум двух завершённых экспериментов.

## MLflow и результаты

Используется один эксперимент `wb-semantic-search`. Каждый повторный запуск создаёт новые runs; текущая сводка хранит одну строку на метод. Метка `evaluation_batch` связывает конфигурации одного запуска, параметр `golden_version` фиксирует данные. В каждый run записываются параметры, все метрики, таблица по запросам, конфигурация и golden-сет. После сравнения добавляются общая таблица, изменения относительно baseline и графики. Для первого эксперимента статистика длинных описаний сохраняется локально в `artifacts/description_sentence_stats.csv`, а парный bootstrap-интервал разницы NDCG@10 рассчитывается в тетради (10 000 выборок, SEED=42). Эти результаты в текущем коде не загружаются в MLflow. Локальные таблицы и снимки перезаписываются; исторические MLflow-runs сохраняются.

После выполнения недели 3:

```bash
python check_mlflow.py wb-semantic-search --env-file .env
```

Успех скрипта подтверждает эксперимент, минимум два успешных run и обязательные метрики и параметры. Дополнительная ячейка тетради проверяет наличие артефактов текущих runs. В сохранённом запуске скрипт завершился успешно. Для пяти текущих validation-runs проверены таблицы, конфигурации, golden-сет и график сравнения; результаты пяти финальных test-runs сохранены в MLflow. История эксперимента содержит повторные запуски, поэтому их число может меняться.

`files/`, `artifacts/`, локальный `.env` и кеши не включаются в Git. Сводные CSV и исходники включаются. В итоговых выводах учитываются синтетические запросы, неполная разметка и ограничение двумя категориями; готовность к промышленному внедрению пока не подтверждена. Streamlit не входит в выбранный объём сдачи.
